# Архитектурные правила проекта (WatchWise)

## 1. Общие положения

- **Архитектурный стиль:** Модульная архитектура (Modular Architecture). Строгое разделение ответственности по техническому назначению папок.
- **Стек:** Next.js 15 (App Router), TypeScript, Prisma, PostgreSQL, Tailwind CSS, Zustand.
- **Язык:**
  - Код (переменные, функции): Английский.
  - Комментарии и документация: Русский.

## 2. Структура папок (`src/`)

Код должен быть распределен строго по следующим директориям. Создание новых корневых папок запрещено без согласования.

### Основные слои:

1.  **`app/` (Routing Layer)**
    - **Назначение:** Маршрутизация Next.js, страницы (`page.tsx`), макеты (`layout.tsx`), API-роуты (`route.ts`).
    - **Правило:** Здесь **НЕТ** бизнес-логики. Файлы здесь только получают данные (через `services`) и рендерят компоненты.
    - **Запрещено:** Писать сложные `useEffect` или прямые запросы к БД внутри страниц.

2.  **`components/` (UI Layer)**
    - **Назначение:** Переиспользуемые React-компоненты.
    - **Структура:**
      - `ui/` — Строго "глупые" базовые компоненты UI-кита (shadcn/ui: Button, Input, Dialog). Не имеют привязки к бизнес-логике.
      - `features/` — Бизнес-компоненты, реализующие конкретную функциональность приложения (например, `VideoPlayer`, `QuizOverlay`).
      - `layout/` — Компоненты каркаса страниц (Header, Sidebar).
    - **Правило:** Компоненты получают данные через пропсы или глобальный стор (Zustand).
    - **Запрещено:** Импортировать `prisma` или вызывать БД напрямую.

3.  **`services/` (Business Logic Layer)**
    - **Назначение:** Ядро приложения. Здесь живет вся логика.
    - **Содержание:** Функции для работы с БД (Prisma), запросы к внешним API (Yandex, YouTube), загрузка файлов.
    - **Правило:** Server Actions должны быть тонкими обертками, вызывающими методы из `services`.

4.  **`server-actions/` (Mutation Layer)**
    - **Назначение:** Функции с директивой `'use server'` для вызова с клиента.
    - **Правило:** Используются для обработки форм и кнопок. Обязательно валидируют входные данные (Zod) и вызывают `services`.

5.  **`store/` (Client State Layer)**
    - **Назначение:** Глобальный клиентский стейт (Zustand). Используется точечно, только для состояния, которое необходимо в разных независимых компонентах (например, счетчик очков `score`).

### Вспомогательные слои:

- **`hooks/`**: Кастомные React-хуки для изоляции сложной логики из компонентов (например, `useVideoQuiz`).
- **`config/`**: Конфигурация сторонних библиотек (экземпляр `prisma`, настройки `logger`).
- **`shared/`**: Общие типы и схемы. Zod-схемы валидации, TypeScript-интерфейсы.
- **`lib/`**: Чистые функции-хелперы, не привязанные к React (парсинг таймкодов, форматирование строк).
- **`constants/`**: Глобальные константы, конфиги таймаутов и игровые механики (`APP_CONFIG`).

## 3. Поток данных и правила импорта

1.  **Server Components (`app/`)** -> вызывают -> **Services (`services/`)** -> вызывают -> **Database (Prisma)**.
2.  **Client Components (`components/`)** -> вызывают -> **Server Actions (`server-actions/`)** -> вызывают -> **Services**.
3.  **Запрещено:** Импортировать файлы из `app/` куда-либо.
4.  **Запрещено:** Вызывать Prisma (`db.ts`) внутри `components/`.

## 4. Обработка ошибок, валидация и безопасность

1.  **Zod:** Все входные данные в `server-actions` и `api` маршрутах должны проходить валидацию через Zod схемы.
2.  **LLM Fallbacks:** Ответы от языковой модели (YandexGPT) валидируются через Zod-схему на сервере. При наличии галлюцинаций происходит очистка строки регулярными выражениями. При критическом сбое на клиент отдается безопасная ошибка через Toast.
3.  **Секреты:** Никогда не хардкодить API-ключи. Использовать только `process.env`.
